--------------------------------------------------------------------------------
1. 협업의 기본 원칙
--------------------------------------------------------------------------------

1.1 단일 진실 원천(Single Source of Truth)
  - README·과제 문서를 먼저 두고, "리드미 보고 짜줘"처럼 **문서 기반 구현**을 요청했다.
  - 효과: 요구사항(R1~R3, 유즈케이스)과 코드가 어긋나지 않게 맞출 수 있다.

1.2 범위를 나누는 요청(Git Flow와 정합)
  - "feature/home만 남기고 지워줘" → 브랜치 단위로 커밋할 수 있게 **기능 단위로 쪼갰다**.
  - 이후 projects, contact를 **별도 요청**으로 붙이는 흐름.
  - 효과: PR/머지 충돌을 예측 가능하게 만들고, 과제의 "feature branching" 요구와 맞춘다.

1.3 산출물 명시
  - "GitHub 이슈 템플릿", "Docker", "pytest", "docs/SETUP.md"처럼 **파일 경로·이름**을 구체적으로 요청했다.
  - 효과: AI가 추측하지 않고 저장 위치까지 맞춘다.

--------------------------------------------------------------------------------
2. 프롬프트 엔지니어링 전략
--------------------------------------------------------------------------------

2.1 제약 조건을 한 번에 주기
  예: "코드 고치지 말고 있는지 여부만 말해줘"
  - 불필요한 수정을 막고, **짧은 판단(Yes/No + 이유)**만 받는다.

2.2 교육/과제 용어를 그대로 붙이기
  예: Lab Part 1(app.py, flask run, curl), Mini-Project 업로드 항목(Requirements.*, README, *.py)
  - 과제 문구를 붙여넣으면 AI가 **체크리스트 형태**로 맞춰 준다.

2.3 TDD 사이클을 단계 이름으로 고정
  예:
    - "실패하는 테스트(RED)만 작성, 구현 없음"
    - "테스트 통과만 목표로 최소 구현(GREEN)"
    - "가독성·확장성 리팩터링, 테스트 유지"
  - 효과: 구현이 테스트보다 앞서 나가는 것을 막고, 보고서/발표에서 **프로세스 서술**이 쉽다.

2.4 구현 위치 충돌 처리
  - 과제는 "app.py에 구현"을 요구할 수 있지만, 테스트는 `from app.profanity import ...`처럼 **패키지 모듈**을 가리킬 수 있다.
  - 전략: (1) 루트 app.py는 Flask 진입점, (2) 도메인 로직은 `app/profanity.py`, (3) 필요 시 conftest에서
    동일 앱 인스턴스에 라우트를 붙이는 방식을 **대화로 정리**했다.
  - 기록: "파일 이름(app.py) vs 패키지 app" 혼동을 줄이려면 README에 한 줄 설명을 두는 것이 좋다.

2.5 사후 규칙 영구화
  - "커밋 메시지는 항상 영어로 추천" → `.cursor/rules/commit-messages.mdc` + `.gitignore`에 `.cursor/` 제외.
  - 효과: 다음 세션에서도 동일한 스타일을 유지한다.

--------------------------------------------------------------------------------
3. 세션에서 반복된 지시 패턴 (요약)
--------------------------------------------------------------------------------

3.1 구현
  - README 기반 Flask + Blueprint(home / projects / contact)
  - 권장 진입 `wsgi.py`, Lab 호환 `app.py` 래퍼, `run.py`, 템플릿·네비 `url_for` 정합

3.2 Git / GitHub
  - 머지 충돌 시: main 갱신 → feature 머지 → 충돌 파일 수동 해결 → 커밋·푸시
  - 이슈 템플릿: bug / feature + config.yml

3.3 배포·환경
  - Dockerfile, docker-compose, .dockerignore
  - docs/SETUP.md: venv + requirements-dev(pytest)

3.4 품질·제출
  - README에 요구 분석·유즈케이스·기능 명세 확장
  - 업로드 전: 라우트·템플릿·의존성·보안(디버그 모드, mailto 등) 점검 요청

3.5 TDD (비속어 마스킹 예시)
  1) 인터페이스만: `mask_profanity(...)` 시그니처
  2) RED: `tests/test_app.py`에 실패 테스트
  3) GREEN: `app/profanity.py` 최소 구현
  4) REFACTOR: 단어 목록·헬퍼 분리로 확장성 강화

[TDD 워크플로우 프롬프트] 
1. RED: 환경 설정 및 실패하는 테스트 작성
"현재 프로젝트에 가상환경과 Pytest 환경을 설정해줘. 그리고 [구현할 기능명, 예: 사용자 로그인]을 위한 **실패하는 테스트 코드(RED)**를 tests/test_app.py에 작성해줘. 아직 실제 코드가 없으므로 테스트는 반드시 실패해야 해."

2. GREEN: 최소 기능 구현 (통과)
"방금 작성한 테스트 코드를 통과시키기 위해 필요한 최소한의 기능만 app.py에 구현해줘. 다른 복잡한 로직은 생략하고 오직 테스트가 **GREEN(Pass)**이 되는 것에만 집중해줘."

3. REFACTOR: 코드 품질 개선
"테스트가 통과했으니, 이제 app.py의 코드를 리팩토링할 차례야. 가독성과 확장성을 고려해서 구조를 개선해주고, 리팩토링 후에도 여전히 테스트가 통과하는지 확인해줘."

4. REVIEW: 전체 구조 및 검증 확인
"전체 웹 라우트와 클라이언트 사이드 연동 로직을 종합적으로 검토해줘. 13시 업로드를 위해 파일 구조가 깔끔한지, GitHub에 푸시하기 전 보안상 결함이나 빠진 의존성 파일(requirements.txt)은 없는지 최종 체크해줘."

5. DOCUMENT: 프롬프트 로그 추출
"오늘 우리가 이 웹 서비스를 만들기 위해 사용한 주요 지시사항과 프롬프트 엔지니어링 전략을 요약해서 docs/prompts.txt 파일로 저장해줘. 어떤 논리로 AI와 협업했는지 명확하게 기록해줘."

로그인 기능 말고 
1. Define Interface: defines only the empty function signature: def
mask_profanity(...)
2. Generate Tests: prompts the AI to generate test cases based on requirements
and saves them to test_profanity.py after review.
3. Implement Code: commands the AI to implement the mask_profanity function
with the goal of "making all failing tests pass."
4. Verify & Refactor: reviews the AI-generated code, improves its quality, and gives
final approval
